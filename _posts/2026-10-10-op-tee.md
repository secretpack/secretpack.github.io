[앞 글](/study/what-is-tee/)에서는 TEE의 기본 개념과 ARM TrustZone이 Normal World와 Secure World를 분리하는 원리를 살펴보았다. 이번 글에서는 그 하드웨어 기반 위에서 실제로 동작하는 대표적인 오픈소스 Trusted OS인 **OP-TEE(Open Portable Trusted Execution Environment)** 를 다룬다.

OP-TEE는 단순히 암호화 기능을 제공하는 라이브러리가 아니다. Secure World에서 동작하는 TEE 운영체제와 Trusted Application(TA)의 실행 환경, 그리고 Normal World와의 통신을 위한 구성 요소를 제공하는 소프트웨어 프레임워크다.

## OP-TEE 개요

- 원래 ST-Ericsson이 개발하였고, 이후 Linaro를 거쳐 현재는 **TrustedFirmware.org** 프로젝트로 오픈소스로 유지되고 있다.
- **GlobalPlatform의 TEE Internal Core API와 TEE Client API를 구현**한다.
- 부트 체인에서 **BL32(= S-EL1의 Trusted OS)** 자리에 위치한다.
- 실제 하드웨어뿐 아니라 **QEMU**에서도 손쉽게 구동할 수 있어, TEE를 학습하고 실험하기에 접근성이 높다.

## 구성 요소

OP-TEE는 하나의 바이너리가 아니라, 두 실행 환경에 걸쳐 동작하는 여러 구성 요소의 집합이다.

**Secure World 쪽**

- **OP-TEE OS (optee_os)** — S-EL1에서 동작하는 보안 커널이다. 스케줄링, 메모리 관리, 암호 연산, TA 로딩을 담당한다.
- **Trusted Application (TA)** — S-EL0에서 동작하는 신뢰 애플리케이션이다. 각 TA는 **UUID**로 식별되며 서명되어 로드된다.

**Normal World 쪽**

- **OP-TEE Linux 커널 드라이버** — `/dev/tee0`, `/dev/teepriv0` 디바이스를 노출하며, SMC를 통해 Secure World와 통신한다.
- **libteec (TEE Client API 라이브러리)** — Client Application(CA)이 TEE를 호출할 때 사용하는 사용자 공간 라이브러리이다.
- **tee-supplicant** — Secure World가 Normal World의 자원(파일 시스템 기반 보안 저장소, RPC 등)을 필요로 할 때, 이를 대신 처리해 주는 데몬이다.

## 호출 흐름 (CA → TA)

Client Application이 TEE 내부의 Trusted Application을 호출하는 전형적인 순서는 다음과 같다.

1. **CA가 Client API로 세션을 연다** — `TEEC_InitializeContext` → `TEEC_OpenSession(UUID)`.
2. **커널 드라이버가 SMC를 발생** — 요청이 Secure Monitor(EL3)를 거쳐 Secure World로 넘어간다.
3. **OP-TEE OS가 대상 TA를 로드·실행** — UUID로 지정된 TA를 S-EL0에서 구동한다.
4. **파라미터는 공유 메모리로 전달** — 두 실행 환경이 합의한 shared memory 영역을 통해 버퍼를 주고받는다.
5. **TA가 연산 수행 후 결과 반환** — 다시 Monitor를 경유해 Normal World로 복귀한다.

이 과정에서 **공유 메모리 경계와 파라미터 검증**은 보안상 가장 민감한 지점이다. Normal World가 전달한 포인터와 크기 값을 Secure World가 검증 없이 신뢰하면 심각한 취약점으로 이어질 수 있다. 실제로 이 경계면은 TEE 보안 연구에서 핵심 공격 표면으로 다루어진다.

## 활용 사례

OP-TEE를 포함한 TEE는 이미 모바일과 임베디드 환경 전반에서 광범위하게 활용되고 있다.

- **키 저장소** — Android Keystore/Keymint의 하드웨어 백엔드
- **생체 인증** — 지문/얼굴 템플릿의 저장·매칭을 TEE 안에서 수행
- **모바일 결제·DRM** — 결제 토큰, 콘텐츠 보호 키 관리
- **디스크/파일 암호화 키 보호**, **원격 증명** 등

## 보안 관점에서의 의의

TEE는 운영체제가 장악된 상황에서도 민감한 자산을 보호하는 것을 목표로 한다. 그만큼 TEE 자체의 견고함이 중요하며, 실행 환경 간 경계(SMC, 공유 메모리, TA 로더, RPC 등)에서 발생하는 작은 결함 하나가 전체 신뢰 모델을 무너뜨릴 수 있다. 따라서 TEE의 구조를 정확히 이해하는 것은 이러한 경계에서 어떤 문제가 발생할 수 있는지 파악하는 출발점이 된다.

## 마치며

이번 글에서는 OP-TEE의 구성 요소와 CA에서 TA로 이어지는 호출 흐름, 그리고 보안 관점에서의 의의를 살펴보았다. 요약하면 다음과 같다.

- **OP-TEE**는 Secure World에서 동작하는 오픈소스 Trusted OS로, GlobalPlatform API를 구현한다.
- 두 실행 환경에 걸쳐 OP-TEE OS·TA(Secure World)와 커널 드라이버·libteec·tee-supplicant(Normal World)로 구성된다.
- CA의 요청은 SMC를 통해 Secure Monitor를 거쳐 TA로 전달되며, 이 **공유 메모리 경계**가 핵심 보안 지점이다.

다음 글에서는 QEMU 환경에서 OP-TEE를 직접 구동하고, 간단한 CA와 TA를 작성하여 호출 흐름을 실제로 확인하는 과정을 다룰 예정이다.
